# Инструкции для coding-агентов

## 1. Назначение проекта и публичный характер

Это персональное публичное портфолио `sl4dk1y`, размещаемое как статический сайт на GitHub Pages. В репозитории нет серверной части, базы данных или собственного API. Любой текст, ссылка, изображение и метаданные, добавленные в сайт или публичные файлы репозитория, следует считать доступными всем.

Показывай только подтверждённые публичные сведения и проекты, разрешённые к публикации. Не придумывай опыт, достижения, результаты, проекты, метрики или технологии. Не раскрывай названия закрытых коммерческих проектов, их внутреннюю архитектуру, исходники, инфраструктуру, метрики и другие непубличные сведения. Общеизвестные технологии можно указывать как навыки, только если они действительно использовались.

## 2. Структура репозитория

- `src/main.tsx` — точка входа, монтирующая React-приложение.
- `src/App.tsx` — одностраничная структура портфолио, навигация, переключатели языка и темы, метаданные страницы.
- `src/components/AmbientGallery.tsx` — условно включаемая декоративная галерея изображений.
- `src/content/portfolio.ts` — публичные данные профиля, список технологий и проектов, SEO-заголовок, описание и URL сайта.
- `src/content/translations.ts` — переводы интерфейса на английский и русский.
- `src/content/artworks.ts` — метаданные иллюстраций, включая пути, размеры, авторство, даты, источники, лицензии, alt-тексты и подписи.
- `src/content/types.ts` — типы локали, темы и структурированных данных портфолио.
- `src/styles.css` и `src/fonts.css` — оформление, адаптивность, темы, эффекты и локальные шрифты.
- `index.html` — HTML-шаблон, начальные SEO-метаданные и англоязычный статический fallback.
- `public/noscript.css` — оформление fallback-версии без JavaScript.
- `public/images/` — локальные изображения профиля и Hero fallback.
- `public/artwork/hero/` и `public/artwork/ambient/` — локальные WebP-иллюстрации Hero и Ambient Gallery.
- `public/artwork/credits.html` — публичная страница источников и атрибуции иллюстраций.
- `public/fonts/` — тексты лицензий для локальных шрифтов; сами WOFF2-файлы поставляются пакетами `@fontsource-variable`.
- `public/robots.txt`, `public/sitemap.xml`, `public/favicon.png`, `public/apple-touch-icon.png`, `public/og-card.svg` — публичные SEO- и графические ресурсы.
- `design-system/sl4dk1y-portfolio/MASTER.md` — действующая визуальная спецификация проекта.
- `vite.config.ts`, `tsconfig*.json`, `eslint.config.js` — конфигурации Vite, TypeScript и ESLint.
- `Dockerfile`, `nginx.conf`, `compose.yaml` — multi-stage сборка и локальный Nginx preview.
- `.github/workflows/pages.yml` — CI-проверки, сборка и деплой GitHub Pages.

Перед изменением выясни, какой файл является источником истины для данных. Не дублируй уже вынесенные в `src/content/` тексты и метаданные непосредственно в компонентах.

## 3. Технологический стек и архитектурные принципы

Проект использует React 19, TypeScript в strict-режиме, Vite 8, CSS, ESLint 10, Node.js 24, Docker Compose и Nginx. Сайт — клиентское статическое приложение без backend/API. Vite настроен с `base: '/'`; адрес GitHub Pages — корень сайта `https://sl4dk1y.github.io/`.

Сохраняй текущую компактную архитектуру: одна страница, небольшие React-компоненты, типизированные данные и локальные статические ресурсы. Сначала проверь существующие компоненты и источники контента; добавляй абстракции только при наличии повторного использования или понятного упрощения. Не переписывай проект без необходимости.

### Minimal Sufficient Change

Сначала разберись в существующей реализации и найди наименьшую точку изменения. Предпочитай исправление существующего кода добавлению нового. Не меняй архитектуру ради небольшой задачи, не создавай универсальную абстракцию для одного случая, лишний слой конфигурации или новый файл, если подходит существующий. Не проводи массовый рефакторинг вне области задачи, не меняй публичные интерфейсы и не дублируй логику или контент без необходимости. Не оптимизируй гипотетические проблемы без подтверждающих данных.

Если есть несколько корректных решений, выбирай то, которое удовлетворяет требованиям пользователя, сохраняет текущее поведение, требует меньше изменений и зависимостей, проще проверяется и сопровождается и не ухудшает производительность. Минимальность не означает пропуск нужных проверок.

TypeScript настроен со `strict`, `noUnusedLocals` и `noUnusedParameters`. Не ослабляй эти проверки и не обходи их через `any`, `@ts-ignore` или приведение типов без обоснованной необходимости. Не добавляй runtime или build-зависимости, если задачу можно решить существующими React, TypeScript, CSS и browser API.

## 4. React, TypeScript и CSS

- Компоненты оставляй небольшими и семантически сфокусированными; повторяющиеся элементы рендери из типизированных данных с устойчивыми `key`.
- Используй существующие React hooks и browser API. Для `IntersectionObserver`, обработчиков событий и подписок обязательно очищай ресурсы при unmount.
- Не переноси тексты, проекты, профильные ссылки или метаданные иллюстраций в JSX, если для них уже предусмотрен модуль данных.
- Сохраняй явные типы для locale, theme, project и artwork; расширяй существующие типы при добавлении новых полей.
- Соблюдай существующие правила ESLint и `react-hooks`; не отключай правила локально для обхода ошибок.
- Оформление реализуй в `src/styles.css` с текущими CSS-переменными и компонентными классами. Не вводи CSS framework или CSS-in-JS библиотеку.
- Сохраняй работу без JavaScript: статическая версия находится в `index.html`, её стили — в `public/noscript.css`. Изменения структуры и копирайта проверяй также в этом fallback, если они должны быть доступны без React.
- Учитывай существующую логику: на первом посещении выбирается Day; `index.html` применяет сохранённую тему до рендера React и переводит устаревшие значения `light`/`dark` в `day`/`night`; переключение языка не меняет тему.

Не превращай страницу в маркетинговый лендинг, не добавляй декоративные карточные сетки, нумерацию или иллюстрации в разделы, где их нет.

## 6. Локализация RU/EN

Английская и русская версии должны оставаться синхронными по структуре и смыслу. Переводимые строки интерфейса размещай в одинаковых ключах `en` и `ru` в `src/content/translations.ts`; двуязычные проектные тексты и подписи находятся в соответствующих структурах `src/content/portfolio.ts` и `src/content/artworks.ts`.

Не добавляй переводимые строки напрямую в JSX или CSS-generated content. Если строка показывается пользователю, обеспечь обе локали, включая `aria-label`, названия действий, навигацию, подписи и сообщения fallback, где применимо. После изменения сверяй, что переключение RU/EN обновляет весь соответствующий текст и локализованные SEO title/description, не меняя выбранную тему. Названия технологий и брендов сохраняй в принятом оригинальном написании.

## 7. Изображения, лицензии и авторство

- Используй локальные оптимизированные файлы в `public/`; не добавляй runtime-загрузку иллюстраций с внешних архивов или CDN.
- Для каждой новой иллюстрации до добавления проверь источник, лицензию и условия атрибуции. Не считай найденное в интернете изображение свободным автоматически.
- Обновляй запись в `src/content/artworks.ts` и страницу `public/artwork/credits.html`: сохраняй автора/создателя, название, дату (если известна), исходный URL, лицензию, локальный путь и двуязычные alt-текст/подпись. Если метаданные неизвестны, не выдумывай их; указывай только проверенные сведения.
- Указывай известные `width` и `height`, чтобы браузер заранее резервировал место. Используй подходящий формат и размер файла; декоративным изображениям задавай пустой alt-текст.
- Не меняй источник, лицензию или attribution существующего artwork без проверки первичных записей и согласованного обновления credits.

## 8. Ambient Gallery

Галерея — декоративный фон, а не основной контент: её корневой элемент скрыт от accessibility tree (`aria-hidden`), а изображения имеют пустой `alt`. Сохраняй эти свойства.

Статичный коллаж включается только при ширине viewport от `1680px` и выключен при `prefers-reduced-motion: reduce`; изображения используют `loading="lazy"` и `decoding="async"`. Левая и правая композиции выбираются независимо, используют разные варианты расположения и три уровня глубины. Каждое изображение появляется не более одного раза, а иллюстрации Hero исключаются. Не загружай изображения на узких экранах и не добавляй таймеры, canvas, анимации или обработчики прокрутки. При изменении порога или набора ресурсов снова проверь мобильную нагрузку, безопасность центральной зоны и reduced motion.

## 9. Accessibility, адаптивность и SEO

- Сохраняй семантические landmarks, один основной `h1`, skip link, нативные ссылки-якоря и видимый клавиатурный focus.
- Интерактивные элементы должны быть доступны с клавиатуры, иметь понятные локализованные accessible names и корректные состояния (`aria-expanded`, `aria-pressed`, `aria-current` там, где они используются).
- Не передавай смысл только цветом или движением; поддерживай достаточный контраст во всех пяти темах. Для внешних ссылок, открываемых в новой вкладке, сохраняй `rel="noreferrer noopener"`.
- Проверяй адаптивную вёрстку как минимум на ширинах 375, 768, 1024 и 1440 px; не допускай горизонтального переполнения и слишком длинной меры текста.
- Учитывай `prefers-reduced-motion`: reveal-эффекты должны не скрывать содержание, а движение галереи должно отключаться. Без JavaScript статический fallback должен сохранять читаемость и рабочие якоря.
- Сохраняй title, description, Open Graph/Twitter metadata, canonical/public URL, `robots.txt` и `sitemap.xml` согласованными с публичным доменом и фактическим содержанием. Не добавляй ложные структурированные данные или SEO-утверждения.

## 10. Безопасность и конфиденциальность

Никогда не помещай в сайт, репозиторий, `AGENTS.md`, логи или примеры секреты, токены, пароли, приватные URL, локальные пути пользователя, внутренние конфигурации, закрытые исходники, сведения о клиентах или непубличные метрики. Не добавляй такие данные даже в комментариях и тестовых примерах. Используй только публичные ссылки, уже предназначенные для портфолио, либо предварительно подтверждённые публичные адреса. Не добавляй аналитику, внешние скрипты или сетевые интеграции без явной необходимости и оценки раскрываемых данных.

## 11. Зависимости

Сначала решай задачу средствами уже установленных пакетов и стандартных browser API. Не добавляй тяжёлые библиотеки, UI framework, анимационные движки или utility-пакеты ради единичной небольшой функции. Если зависимость действительно необходима, проверь размер/назначение, совместимость с Node.js 24 и Vite, лицензию и влияние на production bundle; обнови lockfile штатным пакетным менеджером. Не обновляй несвязанные зависимости в рамках локальной задачи.

## 12. Agent Skills & Workflow Policy

Используй специализированные skills только тогда, когда задача соответствует их назначению. Перед каждым использованием проверь, доступен ли skill в текущем окружении, найди его фактический `SKILL.md`, прочитай инструкции и ограничения и следуй им вместе с этими правилами. Не угадывай команды и возможности по одному названию. Не устанавливай повторно уже доступный skill. Если нужный skill отсутствует, сообщи об этом в отчёте и продолжай обычным способом, если задача остаётся выполнимой. При конфликте приоритет имеют прямые требования пользователя и фактическое состояние проекта.

### UI UX Pro Max

Используй `UI/UX Pro Max` при создании или изменении интерфейсных компонентов, визуального дизайна, типографики, цветов, адаптивной вёрстки, Hero или Ambient Gallery. Сохраняй утверждённую концепцию и токены из раздела «Дизайн-система» и файла `design-system/sl4dk1y-portfolio/MASTER.md`. Полный редизайн допустим только по явному запросу.

### Humanizer

Используй `Humanizer` при написании или редактировании публичных текстов портфолио: About, описаний проектов, RU/EN переводов и публичной документации. Не применяй его к исходному коду, техническим идентификаторам, командам и API. Не добавляй неподтверждённые достижения, опыт или технологии.

### Agent Safe Flow и этапы работы

Под Agent Safe Flow здесь понимается выбор подходящего процесса из доступных skills, а не обязательный запуск одного общего skill. Для этапов используй соответствующие skills, если они установлены: `Spec` — уточнение и фиксация требований; `Audit` — read-only проверка; `Build` — реализация согласованных изменений; `Review` — независимая проверка результата; `Release Check` — проверка готовности к выпуску. Учитывай ограничения каждого `SKILL.md`.

Для небольшого исправления используй облегчённый процесс. Для крупного изменения при необходимости пройди этапы `SPEC → AUDIT → BUILD → REVIEW → RELEASE CHECK`; это порядок возможных этапов, а не обязательный чек-лист для каждой задачи. Не объединяй `AUDIT` и `BUILD`, если пользователь разделил их на отдельные задачи. Ни один skill не разрешает агенту выполнять запрещённые здесь Git-операции или публиковать сайт.

### Context Waypoint

Используй `Context Waypoint` согласно правилам проверки доступности, применения и сохранения контекста в разделе 13.

### Codebase Atlas

Используй `Codebase Atlas`, когда пользователь явно просит архитектурную визуализацию, walkthrough по коду, Mermaid-диаграмму или создание/обновление архитектурной документации. Для диаграмм компонентов, потоков данных, сборки и deployment показывай только подтверждённые исходниками связи. Не запускай Atlas после обычных изменений кода и не создавай диаграммы ради диаграмм. Не путай Codebase Atlas с Codebase Memory: Atlas формирует архитектурные представления, Memory помогает искать узлы и связи в коде.

### Общие правила использования skills

- Выбирай минимальный набор skills, нужный для текущей задачи; не запускай их все автоматически.
- Не устанавливай дополнительные skills без согласования. При отсутствии подходящего skill продолжай стандартным способом, если это безопасно и выполнимо.
- Не записывай приватные сведения в документацию, контекст, отчёты или диаграммы.
- Не добавляй корневой `AGENTS.md` в `.gitignore`; не создавай вложенные `AGENTS.md` без реальной необходимости.

## 13. Design Engineering & Visual Quality

### Использование дизайн-скиллов

- Для задач по UI/UX сначала изучи применимые `AGENTS.md` и действующую `design-system/sl4dk1y-portfolio/MASTER.md`. Выбирай все skills, подходящие характеру задачи, и читай их `SKILL.md` перед применением. Skills дополняют проектные решения, но не заменяют `MASTER.md`; не запускай каждый skill для небольшой CSS-правки.
- `frontend-design` (`~/.agents/skills/frontend-design/SKILL.md`) используй для визуальной композиции, эстетики, типографики и согласованности frontend-оформления.
- `web-design-guidelines` (`~/.agents/skills/web-design-guidelines/SKILL.md`) используй для проверки accessibility, responsive behavior, UX и интерактивных состояний.
- `design-system` применяй, когда задача затрагивает архитектуру дизайн-токенов или спецификации компонентов. Не устанавливай уже доступные глобальные skills повторно и не создавай их копии в репозитории.
- При задачах по UI, frontend, адаптивности и визуальному качеству используй `emil-design-eng`, если он доступен и задача подходит под его фактический `SKILL.md`.
- Для мобильного UX, touch-взаимодействий и проверки поведения на реальных мобильных устройствах используй `mobile-native`.
- Для целенаправленной проверки интерфейса на крайних значениях и нестандартных данных используй `break-ui`. Не запускай его автоматически при обычной вёрстке; не оставляй в публичной версии фиктивные проекты или переключатель тестовых данных.
- Продолжай использовать `UI/UX Pro Max` как дополнительный источник рекомендаций. Сначала проверь наличие каждого skill и прочитай актуальный `SKILL.md`; выбирай только те, что нужны для задачи.

### Визуальные ограничения портфолио

Сохраняй editorial/minimal концепцию с классической типографикой и историческими ботаническими иллюстрациями. Следуй `design-system/sl4dk1y-portfolio/MASTER.md`, палитре, локальным Source Sans 3 и Source Serif 4 и текущей визуальной иерархии. Сохраняй пять тем (Day, Sunset, Forest, Rain, Night), RU/EN и адаптивную компоновку. На первом посещении включается Day; выбор темы сохраняется независимо от языка, а старые значения `light` и `dark` мигрируют в `day` и `night`.

Hero выбирает локальную иллюстрацию при загрузке страницы; не меняй её только из-за переключения языка или темы и сохраняй зарезервированную геометрию. Ambient Gallery — статичная боковая композиция: не добавляй параллакс, автосмену изображений или постоянное движение. Сохраняй её отключение на узких экранах и при `prefers-reduced-motion`, локальную загрузку и подтверждённую лицензию с атрибуцией для каждого изображения. Не добавляй новые анимационные зависимости.

При UI-изменениях проверяй типографику, иерархию, ритм отступов, выравнивание, контраст, навигацию, доступность, производительность, длинные тексты RU/EN, отсутствие горизонтальной прокрутки и layout shift. Не меняй дизайн автоматически по рекомендациям skill: область изменений определяется текущей задачей и согласованными требованиями. Не выполняй редизайн без явного запроса.

### UI/UX Audit

Для явно запрошенного read-only UI/UX AUDIT сначала изучи текущие ограничения и релевантные дизайн-скиллы. Оцени desktop, tablet и mobile, все пять тем и RU/EN; для каждого замечания укажи приоритет `Critical`, `High`, `Medium` или `Low`, причину, последствия и конкретную рекомендацию. Отделяй проверяемые ошибки от субъективных стилистических предложений. Во время AUDIT не исправляй код. Не проводи редизайн без отдельного согласования владельца.

## 14. Исследование репозитория и управление контекстом

### Codebase Memory

Если Codebase Memory доступен, используй его как основной способ навигации по коду. Сначала определи область задачи и проверь индекс. Если текущий проект ещё не индексирован, запусти `index_repository` до графового поиска. Для навигации следуй порядку: `search_graph` для поиска символов, `trace_path` для связей и вызовов, `get_code_snippet` для релевантного исходника, `query_graph` для сложных связей и `get_architecture` для обзора. Используй `search_code` и обычный поиск по файлам для строковых литералов, конфигураций и случаев, когда граф не дал достаточного ответа.

Индекс — навигационная подсказка, а не источник истины: проверяй существенные выводы по актуальным исходникам и конфигурации. Если индекс устарел или покрытие недостаточно, переходи к точечному поиску и чтению файлов; не индексируй заново без необходимости. Не изменяй Codebase Memory или его ADR автоматически в рамках обычной реализации. Если он недоступен, используй ограниченный поиск по релевантным файлам и сообщи об ограничении, когда оно повлияло на результат.

### Context Waypoint

Проверь наличие skill и проектной директории `.context-waypoint/` перед использованием. Применяй Context Waypoint для передачи долговременного контекста после значимых проверенных изменений архитектуры, deployment или крупных функциональных блоков, а также когда пользователь просит сохранить состояние. Не создавай записи после мелкой правки. Если проектной директории нет, следуй фактическому `SKILL.md`: инициализируй её только когда долговременная непрерывность действительно полезна; иначе оставь компактную сводку в текущей задаче. Записывай только проверенные факты, решения, ограничения, результаты проверок и необходимые дальнейшие шаги; не сохраняй секреты или приватные сведения.

### Ponytail

Перед применением проверь, установлен ли Ponytail и доступен ли его `SKILL.md`; используй только подтверждённые возможности установленной версии. Если Ponytail отсутствует, не устанавливай его и не создавай собственную замену: ограничь чтение нужными фрагментами, не повторяй уже выполненное исследование и переноси между этапами краткую структурированную сводку.

### Экономное исследование и синхронизация

Рабочий порядок: прочитать задачу и применимые инструкции; определить границы; проверить доступность релевантных инструментов; найти файлы и связи; прочитать только необходимые фрагменты; кратко спланировать; внести минимальное изменение; выполнить нужные проверки; подготовить компактный отчёт. Не сканируй весь репозиторий и не читай `node_modules`, `dist` или другие generated directories при обычной задаче. Не повторяй завершённые проверки и не выводи большие логи без необходимости. Полный аудит, расследование безопасности и подготовка к выпуску могут требовать более широкого охвата.

После значимой реализации сначала заверши BUILD и REVIEW. Если по задаче требуется синхронизировать документацию, Context Waypoint, Codebase Memory или архитектурные материалы, выполняй эти обновления отдельными этапами после проверки фактического состояния; не объединяй их с BUILD без явной необходимости. Не обновляй Codebase Memory до проверки документации и актуальных исходников. Не записывай неподтверждённое состояние.

## 15. Локальная разработка, проверки и Docker preview

Используй Node.js 24 LTS и npm. После `npm ci` доступные команды из `package.json`:

```sh
npm run dev
npm run typecheck
npm run lint
npm run build
npm run preview
```

`npm run build` выполняет `tsc -b` и `vite build`; production-артефакты создаются в `dist/`. Проверка собранного сайта локально выполняется командой `npm run preview` после сборки.

Для локального Nginx preview доступны Docker Engine и Docker Compose:

```sh
docker compose up -d --build
docker compose ps
docker compose logs -f
docker compose down
```

Compose собирает `Dockerfile` (Node.js 24 Alpine build stage и Nginx Alpine preview stage), отдаёт статику из `dist/`, публикует порт только на `127.0.0.1:8080`; альтернативный порт задаётся через `PREVIEW_PORT`, например `PREVIEW_PORT=8081`. Health endpoint Nginx — `/healthz`. Preview нужен для локальной проверки и сам по себе не публикует сайт.

## 16. GitHub Pages deployment и Git-политика

GitHub Pages использует workflow `.github/workflows/pages.yml`: настраивает Node.js 24, выполняет `npm ci`, `npm run typecheck`, `npm run lint`, `npm run build`, загружает `dist/` и затем деплоит Pages artifact. Workflow запускается при push в `main` и через `workflow_dispatch`; следовательно, push в эту ветку способен автоматически опубликовать сайт. Vite `base` должен оставаться согласованным с целевым корневым доменом.

Все Git-операции выполняет исключительно пользователь. Агентам запрещено запускать `git add`, `git commit`, `git push`, `git merge`, `git rebase`, `git tag`, `git reset`, `git checkout` с изменением рабочего дерева, `git clean`, создавать релизы или публиковать сайт. Не изменяй историю Git. Разрешены только read-only проверки `git status`, `git diff`, `git log`, однако для задач, где они не нужны, не запускай их. Не запускай Pages workflow, `workflow_dispatch` или иные команды публикации без отдельного разрешения пользователя.

## 17. Проверки перед завершением задачи

Для изменений приложения запускай проверки, предусмотренные проектом: `npm run typecheck`, `npm run lint` и `npm run build`. Если среда не позволяет запустить какую-либо проверку, сообщи об этом, не заявляя успех. Не выдумывай результаты.

Дополнительно проверь релевантное изменению:

- RU и EN: полноту и соответствие переводов; переход между языками не должен менять тему.
- Все пять тем: читаемость, контраст, границы, выделение, фокус и состояния controls.
- `index.html` / `public/noscript.css`: fallback без JavaScript, если изменение затрагивает структуру или критичный текст.
- Адаптивные ширины 375, 768, 1024 и 1440 px, если менялась вёрстка.
- `prefers-reduced-motion`, если затронуты анимации, reveal или Ambient Gallery.
- Изображения и credits, если менялись artwork, лицензии или метаданные.
- Публичность новых данных, ссылок и навыков; отсутствие секретов и непубличной информации.

Не запускай действия, изменяющие Git или публикующие сайт. Не утверждай, что визуальная или runtime-проверка выполнена, если фактически проверялись только исходники или сборка.
